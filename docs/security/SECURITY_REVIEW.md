# Security and financial correctness review

2026-11-23; static source review of the SHAs in [REPO_COMPARISON](../architecture/REPO_COMPARISON.md). Findings below distinguish observed code from unverified exploitability/deployment. No exploit or live Tally request was executed.

## Trust boundaries and threat model

Assets: ledger/voucher data, company identifiers, reports, employee identity, tokens/secrets, Tally availability and integrity. Threat actors include unauthenticated internet clients, authenticated users exceeding their company scope, malicious content in narration, compromised local accounts and compromised dependencies. Boundaries: cloud agent to HTTPS ingress; proxy to authenticated backend; identity to company/tool policy; XML response to trusted financial model; report owner to download consumer; Windows service to host resources.

The LLM is an untrusted orchestrator. Tool descriptions, readOnlyHint and prompts are not security enforcement. Authentication is necessary but does not confer permission to every company or report. A local compromise remains serious on a same-VM deployment; minimize the service account's file and execution rights.

## Financial correctness findings

1. **F01 P0 for trusted reporting:** MVP parseAmount uses parseFloat and converts missing/non-numeric input to zero. Prefix strings can parse partially; JS numbers have finite precision. Missing ledger names are skipped. Require strict finite monetary parsing, explicit currency/precision policy, invalid-line failures and balanced/reconciled totals; never silently repair money.
2. **F02 P0:** Both company-list and voucher normalizers can return an empty list for syntactically valid but unexpected XML. STATUS=0 handling is useful but insufficient for all Tally error shapes. Confirm expected response shape, company context and completeness before calling a review successful. Empty company lists and legitimate zero-voucher ranges need distinct results.
3. **F03 P1:** MCP dates use regex; review_vouchers checks ordering but search_day_book does not. REST schema additionally validates calendar dates/order/366 days. Share one schema and add maximum company/name length and output limits.
4. **F04 P1:** Five narration rules are hardcoded. First keyword match wins; a fixed settlement-ledger set means tax, payable, bank aliases and multi-expense entries can be labelled INCORRECT and assigned the same suggested ledger. INCORRECT currently sets humanReviewRequired=false. Keep the deterministic engine but add finance-approved scope/ambiguity handling, COA mappings and mandatory human review for corrections. “Correct” means matched the limited classification rule, not a complete accounting audit.
5. **F05 P1:** GUID/master/composite voucher IDs need company qualification; fallback IDs depend on iteration order. ALTERID is requested but not retained in the normalized contract. Add source/company/revision evidence and distinguish cancellation, optional vouchers, foreign currency, inventory allocations, tax and multi-line scenarios before claiming coverage.
6. **F06 P1:** MVP date filtering happens after retrieval. Confirm the actual collection respects date restrictions in the approved Tally version; otherwise full history may consume memory and expose excessive data before filtering. Enforce verified server-side bounds and bounded retrieval.
7. **F07 P1:** Claudally report numeric/date conversion is report-dependent; transport assumes UTF-16LE and does not visibly reject HTTP status in postTallyXML. MVP uses UTF-8. Add encoding/status fixtures and reconcile the selected adapter on the target build; neither assumption proves universal Tally compatibility.

## Existing protections worth retaining

MVP: loopback default, fixed XML construction and company escaping, HTTP/empty-response errors and timeout, REST date checks, timing-safe secret comparison, header redaction, Excel text sanitization and fixture coverage. Claudally: loopback default, required password, all-method bearer checks, PKCE S256, redirect/client validation, rotating refresh tokens, bounded DCR registry, auth backoff/rate limits, CORS/Host checks, external DuckDB access disabled, read-only guards and template-injection regression tests.

Claudally's old security document contains findings fixed in current source. Dynamic registration is not by itself an authentication bypass: its shared password still gates authorization. Assess DCR policy and exact Copilot callbacks in staging. The current `/mcp` 401 response lacks an explicit WWW-Authenticate resource-metadata challenge in inspected source; discovery interoperability needs a real client test.

## Data handling and operational controls

Approve what accounting data may enter Copilot responses/transcripts and Power Platform storage. Return minimum necessary summaries/evidence; full voucher arrays need explicit scope and bounds. Redact financial payloads from application/proxy logs, crash reports and support bundles. Encryption/ACL controls extend to report storage, backups, paging and dumps; in-memory processing is not a universal “no data residency” guarantee. Review prompt injection with hostile narration, XML metacharacters and spreadsheet text; verify no instruction changes authorization or triggers additional tools.

A Caddy-only edge has no managed WAF or dedicated DDoS isolation. Combined host failure or resource exhaustion can affect Tally. IT must accept residual risk after limits, patching, alerts and ingress controls. Stop pilot on wrong-company access, unexpected mutations, untrusted certificates, reconciliation mismatch or Tally disruption.
